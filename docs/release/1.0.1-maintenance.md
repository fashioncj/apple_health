# fix(sync): prepare HealthSync 1.0.1 maintenance release

HealthSync 1.0.1 (build 11) repairs queued sync recovery, preserves workout identities beyond the original five activity mappings, and exports available workout summaries. It supersedes the export-only build 10 candidate. The candidate keeps bundle ID `com.megabyte0x.HealthSync`, team `9UR77TD484`, and the iOS 17 deployment target.

## Release notes

- Recognizes elliptical, rowing, HIIT, yoga, swimming, hiking, and the other HealthKit workout types.
- Includes available workout heart-rate, METs, and effort summaries; distinguishes active calories from active-plus-basal total calories.
- Sends fresh data before unrelated failed uploads and splits uploads into smaller requests.
- Rechecks recent steps, sleep, and workouts daily to help recover recent missing or enriched data.
- Improves recovery of pending uploads after interruptions and app upgrades.

## Compatibility

Existing SQLite tables, settings, HealthKit anchors, device identity, Keychain credentials, payload field names, and schema versions remain supported. Existing activity names stay unchanged. Newly recognized names use HealthKit's lowerCamelCase names; the explicit Other type remains `other`, and future unrecognized types use `hk_<rawValue>`. Every workout also includes the string-valued `metadata.hk_workout_activity_type`.

No backend migration is required. Custom servers must accept the documented string-valued `activity_type` field and existing metadata dictionary. Optional `average_heart_rate_bpm`, `max_heart_rate_bpm`, `average_mets`, `workout_effort_score`, and `estimated_workout_effort_score` metadata entries contain numeric strings. Effort ratings require iOS 18+ and available HealthKit data. See the [workout summary contract](../../README.md#workout-summaries).

The calorie correction changes the interpretation of `total_energy_kcal`: earlier builds copied active energy into both calorie fields. Newly read workouts retain active calories in `active_energy_kcal` and send total calories only when both active and basal workout energy are recorded. Missing components leave the total absent. Existing pending payloads retain their saved values until superseded by a fresh read. Consumers should read active calories from `active_energy_kcal` and handle an unknown total.

Selecting Workouts requests supporting heart-rate, energy, distance, and effort read permissions. Existing users should request Apple Health permissions again in Settings to enable these summaries. Denied or undetermined effort permission leaves effort fields absent while allowing the workout to sync; other effort read failures remain retryable.

The recent reread covers today and the previous three local calendar days, respects selected types, and excludes heart rate. Sleep queries include samples overlapping the range, including sleep starting before midnight. Raw HealthKit UUIDs and source names/bundle IDs are retained. Historical optimized backfill keeps its existing aggregation behavior. To update older workouts previously exported as `other`, manually backfill the affected date range after installing the update.

The heart-rate exclusion applies to standalone heart-rate samples; associated workout statistics still supply heart-rate summaries. Summaries are refreshed when the workout is read. Late metric or effort edits to workouts older than the rolling reread range require backfilling those dates; this release does not add an incremental effort-relationship tracker.

## Queue recovery guarantees

- Every new incremental chunk is saved before anchors advance or network upload starts.
- Requests contain at most 100 metrics, workouts, or deletions. Existing oversized pending batches are atomically replaced with durable smaller batches.
- Queue normalization retains the newest operation for each device, record kind, and HealthKit ID before applying retry priority. New records, corrections, and deletions atomically supersede older pending snapshots; unrelated queued records remain durable.
- Replacement batches receive new export IDs. Their HealthKit record IDs remain unchanged, and subsequent retries retain the persisted replacement export IDs.
- Fresh work uses one HTTP attempt per batch and stops on failure. Historical unattempted work is limited to three batches per wake; previously failed work is limited to one batch per local calendar day.
- Cancellation stops further network attempts without retiring unacknowledged batches. Negative acknowledgements leave batches pending. Lost replies retain the original request for replay.
- The client does not infer success from the existence of a Hosted `sync_batches` row. The existing server writes that row before all child writes finish, so that inference would be unsafe.

## Automated verification

The XCTest suite covers fresh-before-stale ordering, atomic chunking, legacy queue upgrade and rollback, source-preserving reconciliation, daily policy across daylight saving time, cross-midnight sleep, cancellation, negative acknowledgements, and timeout/restart/replay through URLSession.

The XCTest suite also covers summary units and missing values, active versus total calories, rowing distance, effort query relationships, latest ratings, optional permission denial, read-error propagation, and enrichment during recent rereads and backfill. The FastAPI integration suite covers the existing backend contract, record deduplication, upgrading a workout from `other` to its correct activity, summary round-tripping, and clearing unavailable totals during a reread while retaining its HealthKit ID.

Local release verification passed 102 simulator tests and 26 backend tests. The simulator suite intentionally skips the opt-in physical-workout test. Real-workout conversion and upgrade-preservation checks passed on a connected iPhone, as did both populated elliptical/rowing export fixtures. The fixtures validate conversion, queue persistence, and request JSON using in-memory data; source-app recording and locked-phone background delivery remain device acceptance checks.

The TestFlight workflow runs the complete iOS test suite before signing and exporting. Enable `export_only` to generate a signed IPA without uploading it to App Store Connect. See [TestFlight workflow instructions](testflight-github-actions.md).

## Physical device acceptance before broad rollout

1. Install through TestFlight over the existing App Store app. Confirm the hosted workspace or custom backend, token, selected types, and pending queue survive.
2. Confirm an elliptical/rowing/HIIT workout reaches both a custom backend and Hosted with the correct name, stable HealthKit ID, and raw activity metadata.
   Request Apple Health permissions again. Compare recorded average/max heart rate, active/basal energy, distance, METs, and user/estimated effort against Apple Health. Confirm missing or denied optional data remains absent, and repeat with an older workout using backfill.
3. Interrupt a sync, restore connectivity, and confirm pending counts drain without duplicate health records or resurrection of deleted records.
4. Confirm a late source write and sleep crossing midnight appear after a recent reread, with the original source attribution.
5. Leave the phone locked across best-effort background wakes and inspect freshness, battery use, and pending backlog. iOS scheduling remains best effort.

Simulator tests cannot establish real HealthKit permissions, source-app timing, or iOS background delivery on a physical phone. These device checks are the acceptance gate for rollout beyond the maintenance beta.
